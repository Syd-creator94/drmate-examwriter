# Технический паспорт ExamWriter-прототипа

## 1. Назначение

Документ описывает ExamWriter-контур внутри Dr. Mate: пайплайн преобразования
отчётов ExamWriter/OfficeMate в компактное русскоязычное офтальмологическое
заключение. Актуальное состояние всего проекта, включая справочник контактных
линз, ведётся в `docs/project/status.md`.

Целевая цепочка:

```text
ExamWriter RTF/TXT
  -> адаптер ExamWriter
  -> нормализованная JSON-модель
  -> HTML/CSS-шаблон
  -> PDF
  -> печать
```

Главная идея: отделить грязный источник данных от универсальной медицинской модели и печатного дизайна. Это важно для будущего Dr. Mate, потому что ExamWriter должен быть только одним из возможных источников, а не центром архитектуры.

## 2. Текущее состояние

Статус: рабочий ранний прототип.

Исходный коммит ExamWriter-ядра: `f9b1d6b Initial ExamWriter medical record pipeline`.
Текущую ревизию репозитория следует проверять командой `git rev-parse HEAD`.

Основные части:

- `dr_mate_core`: универсальная Pydantic-модель медицинской карты и нормализаторы.
- `dr_mate_adapters.examwriter`: чтение RTF/TXT, извлечение текста, разбор секций ExamWriter.
- `dr_mate_rendering`: HTML-шаблон, Playwright PDF-рендер и запасной ReportLab PDF-рендер.
- `dr_mate_cli.py`: CLI-команда для ручного запуска.
- `templates/medical_record.html.j2`: печатный HTML/CSS-шаблон A4.
- `examples/examwriter_sample.rtf`: тестовый пример.
- `tests/`: базовые pytest-тесты.

## 3. Что программа уже умеет

- Читать простой ExamWriter-подобный `.rtf` или текстовый экспорт.
- Извлекать текст из RTF без Word COM и без Windows-зависимости.
- Раскладывать данные в нормализованную JSON-модель `MedicalRecord`.
- Генерировать HTML-заключение на русском языке.
- Генерировать PDF:
  - основной целевой путь: Playwright/Chromium из HTML/CSS;
  - аварийный путь: ReportLab напрямую из JSON-модели, если браузер недоступен.
- Устойчиво переносить отсутствующие блоки: если нет очков, кератометрии, процедур или назначений, модель не ломается.
- Прогонять базовые тесты парсинга, нормализации и HTML-рендера.

## 4. Реализованные нормализации

- `RT`, `Right` -> `OD`.
- `LT`, `Left` -> `OS`.
- `Bilateral`, `BI`, `Both` -> `OU`.
- Даты `MM/DD/YYYY` -> `DD.MM.YYYY`.
- Snellen `20/20`, `20/25`, `20/40` -> десятичная острота зрения.
- `16"` -> `40 см`.
- Оси кератометрии и рефракции приводятся к трем цифрам: `85` -> `085`.
- Диоптрии форматируются с двумя знаками: `-4.25 -0.50 x 050`.
- `Dominant eye RT` -> `Доминантный глаз: правый`.
- `OBSERVATIONS` -> `(заметки)`.
- Семейный анамнез приводится к клиническому виду: `Myopia Sister` -> `Миопия: у сестры`.
- Одинаковые диагнозы OD/OS объединяются в `OU`.

## 5. Плюсы для будущего Dr. Mate

### Архитектурная независимость

ExamWriter вынесен в отдельный adapter. Универсальная модель `MedicalRecord` не зависит от ExamWriter, OfficeMate, Word, RTF или конкретной формы печати. Это позволяет позже добавить другие источники данных.

### Чистая медицинская модель

JSON-модель уже становится внутренним контрактом Dr. Mate. Поверх нее можно строить:

- PDF-генератор;
- локальный API;
- React-интерфейс;
- редактор заключения;
- автоматическую проверку полноты данных;
- историю изменений;
- экспорт в другие форматы.

### Печатный дизайн отделен от парсинга

HTML/CSS-шаблон не занимается извлечением данных. Он получает уже нормализованную модель. Это значит, что внешний вид можно улучшать отдельно от медицинской логики.

### Отказ от Word COM

Проект стратегически уходит от `pywin32 + Word COM`, а значит снижает зависимость от Windows Server 2012 R2, установленного Microsoft Word, COM-ошибок, зависших процессов Word и медленной автоматизации.

### Тестируемость

Парсинг и нормализации уже покрываются pytest. Это важная база для работы с реальными ExamWriter-файлами, где каждое новое исключение можно превращать в fixture и тест.

## 6. Слабые стороны текущего состояния

### Парсер пока демонстрационный

Он работает на тестовом ExamWriter-подобном примере, но еще не обучен на настоящем разнообразии RTF из клиники. Реальные файлы могут содержать другие заголовки, вложенные таблицы, странные переносы, дубли, шаблонные фразы и скрытые RTF-конструкции.

### Нормализации неполные

Есть базовая нормализация глаз, дат, остроты зрения, расстояния, осей, диоптрий, анамнеза и диагнозов. Но еще нет полного клинического словаря, правил для всех диагнозов, всех видов Rx, контактных линз, фории, IOP, slit lamp, fundus, OCT и других блоков.

### Нет редактора перед печатью

Сейчас программа генерирует заключение автоматически. Для будущего Dr. Mate желательно иметь экран просмотра и ручной правки перед финальной печатью.

### HTML/PDF путь нужно проверить вне Codex

Код поддерживает Playwright/Chromium, но в текущей песочнице Codex запуск Chromium был заблокирован системными ограничениями macOS. Поэтому демонстрационный PDF был создан через ReportLab fallback.

### ReportLab fallback не равен целевому дизайну

ReportLab полезен как аварийный путь, но главный печатный дизайн должен жить в HTML/CSS. HTML проще развивать, легче визуально настраивать и лучше подходит для будущего интерфейса Dr. Mate.

### Нет hot-folder режима

Пока запуск ручной через CLI. Следующий практический слой - папка, куда ExamWriter сохраняет RTF, а программа автоматически делает JSON/HTML/PDF.

## 7. Что значит проверить Playwright/Chromium PDF без песочницы Codex

Это значит запустить тот же проект в обычной пользовательской среде, где Chromium имеет право стартовать как нормальное приложение.

В текущем Codex-сеансе код выполняется внутри управляемой песочницы. Она разрешает читать и писать файлы в проекте, но ограничивает некоторые системные действия. Chromium на macOS при запуске использует системные механизмы, в том числе регистрацию служебных процессов. В песочнице Codex это было заблокировано, поэтому браузер скачался, но не смог стартовать.

Это не означает, что нужно сразу создавать отдельное полноценное macOS-приложение.

Для проверки достаточно обычного запуска проекта на машине врача или разработчика:

```bash
python3.12 -m venv .venv
. .venv/bin/activate
python -m pip install -e ".[dev]"
python -m playwright install chromium
drmate-examwriter examples/examwriter_sample.rtf --outdir outputs
```

Если эта команда создает `outputs/examwriter_sample.pdf`, значит Playwright/Chromium работает нормально.

## 8. Нужно ли делать отдельное приложение в macOS

Не сейчас.

На данном этапе отдельное macOS-приложение не требуется. Правильнее сначала укрепить ядро:

1. надежный парсинг реальных ExamWriter RTF;
2. стабильная JSON-модель;
3. хороший HTML/CSS-дизайн;
4. автоматический PDF;
5. hot-folder режим.

После этого можно выбрать упаковку:

- простой локальный CLI-скрипт;
- background service с hot-folder;
- маленькое desktop-приложение;
- локальный FastAPI-сервис;
- полноценный Dr. Mate UI на React/TypeScript.

Отдельное macOS-приложение имеет смысл позже, если нужно удобное окно, настройки, кнопка печати, просмотр результата и автозапуск. Но для проверки Playwright оно не нужно.

## 9. Рекомендуемые следующие шаги

1. Собрать 5-10 анонимизированных реальных RTF из ExamWriter.
2. Для каждого файла сохранить ожидаемый JSON-результат как fixture.
3. Расширить parser под реальные секции ExamWriter.
4. Добавить слой `raw -> normalized -> clinical_summary`, чтобы не терять исходные значения.
5. Улучшить HTML/CSS-шаблон по реальному образцу печатного заключения.
6. Проверить Playwright/Chromium на обычной машине вне Codex.
7. Добавить hot-folder режим через `watchdog`.
8. После стабилизации ядра подумать о локальном UI Dr. Mate.
